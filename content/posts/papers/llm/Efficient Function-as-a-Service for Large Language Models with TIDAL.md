## AI Summary

### **论文: TIDAL - 为大型语言模型设计的高效函数即服务 (FaaS)**

这篇论文针对在“函数即服务”（FaaS）平台上部署大型语言模型（LLM）时遇到的严重“冷启动”问题，提出了一个名为 **TIDAL** 的优化框架。

#### **一、 问题背景：LLM 在 FaaS 平台上的挑战**

1. **高昂的冷启动开销**：LLM 应用具有计算密集和调用模式零散的特点，非常适合 FaaS 模式 。然而，LLM 的巨大体积和复杂的运行环境，使得 FaaS 的冷启动问题变得异常严峻，尤其是在 GPU 层面 。
2. **GPU 冷启动的瓶颈**：一个完整的冷启动过程包括：将模型从存储加载到主机内存，再从主机内存传输到 GPU 显存，最后在 GPU 上执行推理 。即便优化了第一步（存储到主机内存），第二步（主机到 GPU 的数据传输）和首次执行内核的开销仍然是主要的性能瓶颈 。
3. **传统方案的局限性**：
    - **简单的模板启动 (Template-start)**：一种常见的方法是预先在 GPU 上初始化好一个模型实例作为“模板”，新请求直接从模板启动以跳过初始化。但这种方法对 LLM 来说存在三个核心缺陷：
        - **模板密度低**：LLM 模型巨大（如 Llama2-13B 占用超过 24GB 显存），导致一块 GPU 只能容纳一两个模板，这在需要支持多租户的 FaaS 平台中是不切实际的 。
        - **无法处理动态性**：许多 LLM 应用会根据用户请求动态加载特定的 LoRA 适配器 。这种请求相关的初始化过程使得模板无法被静态保存和复用 。
        - **内核调用仍然“冷”**：GPU 的内核代码段是在首次被调用时才“懒加载”到显存的 。因此，即使模型数据已经在显存中，第一次推理依然会因为内核懒加载而产生显著延迟 。

#### **二、 TIDAL 的核心思路：洞察并利用“细粒度执行路径”**

TIDAL 的核心洞见在于：

**要优化 LLM 的冷启动，关键在于理解其从初始化到推理全过程中的“细粒度执行路径”** 。这个路径揭示了模型权重（weights）是如何被加载、传输，以及它们与具体计算（GPU 核函数）之间的依赖关系 。通过揭示这些原本隐含的依赖关系，TIDAL 找到了新的优化机会。

#### **三、 TIDAL 的关键方法与技术**

为了实现上述思路，TIDAL 设计了以下几个关键模块和优化技术：
**1. 轻量级的执行路径追踪 (Lightweight Tracing)**

- TIDAL 能够自动、透明地追踪 LLM 函数的执行路径，无需开发者手动修改代码 。
- 它采用了一种**“以权重为中心的两阶段追踪”**策略 ：
  - **初始化阶段 (Strict Tracing)**：严格追踪与模型权重相关的操作（如内存分配、数据复制），构建数据流图（DFG），从而区分哪些是静态不变的（如基础模型），哪些是动态变化的（如 LoRA 适配器） 。
  - **推理阶段 (Lax Tracing)**：宽松地追踪权重在推理过程中的**访问顺序**以及它们所调用的 **GPU 内核** 。

**2. 自适应函数模板 (Adaptive Function Template)**

- 利用追踪到的信息，TIDAL 会为每个 LLM 函数生成一个“自适应”的模板 。这个模板包含三个核心部分：
  - **必需的 GPU 内核信息**：存储了经过“去重”处理的、该函数推理所必需的 GPU 内核列表，为后续的预热做准备 。
  - **重排序的权重布局**：根据追踪到的访问顺序，对模型的权重进行重新组织。这使得后续的“边加载边计算”效率最高 。
  - **权重的数据流图 (DFG)**：用于在运行时快速判断一个权重是静态还是动态的，从而决定是直接复用还是重新初始化 。

**3. 核心启动优化技术**

基于自适应模板，TIDAL 实现了两大优化：

- **主动式代码段加载 (Proactive Code Segment Loading)**
  - 在函数调用前，TIDAL 利用模板中记录的内核信息，在一个预热好的进程中提前触发这些内核的加载 。
  - 这就在真正调用发生前，将所有必需的 GPU 内核代码段加载到了显存中，从而彻底消除了首次推理时的“内核冷启动”延迟 。
- **自适应状态复刻 (Adaptive State Forking)**
  - 当一个新请求到达时，TIDAL 不再是简单地复制整个模板，而是进行“自适应复刻” 。
  - **静态部分复用**：对于模型的静态部分（如基础权重），TIDAL 直接跳过初始化，通过指针复用模板中的状态 。
  - **动态部分初始化**：对于动态部分（如请求特定的 LoRA 适配器），TIDAL 则正常执行用户的初始化代码来加载它们 。
  - **计算与加载重叠**：这是 TIDAL 最重要的优化之一。对于模板中没有完全预加载到 GPU 的权重，TIDAL 会在 GPU **执行推理计算的同时**，从主机内存异步地将后续计算所需的权重数据传输到 GPU 。由于追踪到了权重的精确访问顺序，TIDAL 可以保证数据在被使用前一定就绪，从而最大化重叠效率，将冷启动时间缩短为“加载时间”和“推理时间”中的较大者 。

#### **四、 实验结果与贡献**

- **显著的性能提升**：实验表明，与当前最先进的方案（如 ServerlessLLM）相比，TIDAL 能够将 LLM 函数的冷启动延迟降低 **1.79 倍至 2.11 倍** 。
- **真实世界负载下的表现**：在模拟真实世界请求负载的场景下，TIDAL 成功将 95 百分位的首次出词时间（TTFT）减少了 **76.0%** 。
- **高可扩展性**：TIDAL 的优化方法同样适用于多 GPU 的分布式推理场景，并表现出良好的扩展性 。

#### **五、 结论**

TIDAL 框架通过其创新的“细粒度执行路径追踪”和“自适应模板”技术，精准地解决了 LLM 在 FaaS 平台上的 GPU 冷启动难题。它不仅能处理动态 LLM 函数，还能通过计算与数据传输的深度重叠，实现了极高的启动效率和资源利用率，为在无服务器架构上高效部署和运行 LLM 应用提供了强大的解决方案。
